# 开源 Fork 发布约定

本项目的公开版本以 [kelai141/dsh-mobile-apk](https://github.com/kelai141/dsh-mobile-apk) 的正式 GitHub Fork 为基础。保留上游公开历史和许可证；NAS 是私有开发协作源，不作为公开仓库的历史来源。本文件是发布流程，不是验收通过声明。

## 历史与目录

1. 发布获授权后创建上游 Fork，在独立目录 checkout。记录经验证的上游提交；不能将 NAS remote 改成 GitHub 后直接 push，也不能合并 NAS 分支或使用 `--mirror` / `--all`。
2. 用 `git archive <已审核提交>` 导出下游源码，禁止复制整个工作目录、`.git`、本地 refs、忽略文件或设备快照。只有已审核的路径进入导出清单。
3. 上游的 Android 工程位于根目录，本地位于 `android-shell/`，根部还有下游工具与文档。导入前记录逐目录映射及同名文件处理，不能直接覆盖同名 `scripts/`、`docs/`、README 或 LICENSE。
4. 如保留当前构建路径，可先在 Fork 中用单独提交将上游工程移至 `android-shell/`，保留根部许可证入口，再应用下游树；移动提交不得夹带业务修改。另一方案是保持上游根布局并移植下游路径，须重新验证构建。目录布局本身不决定 Fork 关系，但会影响后续同步和 PR 审阅成本。
5. 核对新增提交的祖先只有预期上游历史，不包含任何 NAS 私有提交；分别审计最终树、新增提交和继承历史。上游历史中的公开测试凭据不能被误报为本地新泄漏，也不能因来自上游就用于正式签名或认证。
6. 只推送明确审核的公开分支。作者署名、提交邮箱和提交说明也属于公开内容；新提交使用确认可公开的身份。已有第三方版权身份不得作为“隐私清理”删除。

## README 与许可

README 应介绍下游的真实功能、与上游的关系、维护者、安装/构建入口、限制和支持渠道。可重写介绍与示例，但保留版权、许可及必要归属；不要沿用上游下载入口让用户误装另一发行版。原版完整说明可链接固定上游提交。

- 保留安卓壳 MIT 原文、kelai141 版权、各组件 LICENSE/NOTICE 和随包声明。README 致谢不能替代许可全文。
- 新增的自有脚本、文档、原生代码与独立插件增量采用根目录 MIT 许可证，许可边界与贡献署名见 `../LICENSING.md`；第三方修改仍遵守来源许可，不能替第三方补造授权或版权信息。
- 每个 vendored 第三方包记录名称、版本/提交、来源、许可全文及修改说明。`package.json` 中单独的 `"license": "MIT"` 不能代替检查发行物中的版权/许可文本；缺失时核对固定版本源码/发行包或取得作者确认。
- 图片、图标、视频、音频独立记录来源与允许分发的范围。维护者已确认海底启动视频为其 AI 生成素材，允许随开源项目分发，范围见 `../android-shell/artwork/startup/README.md`。其他素材不能仅凭二进制哈希白名单推定授权。不得把生成标识或数字签名误当 API Key，也不为通过扫描删除来源标识。
- 插件若独立打包分发，应检查其包内许可，而非依赖父仓库中的 LICENSE。

## 凭据与隐私门禁

先执行 [REPOSITORY-HYGIENE.md](REPOSITORY-HYGIENE.md) 中的暂存对象扫描，并用独立凭据扫描器检查干净导出树及拟公开历史。报告只保存在忽略目录，输出路径、规则、摘要和脱敏结果；不要输出或请求验证疑似真实密钥。

检查 API Key、OAuth/会话令牌、Cookie、ADB 身份、签名文件、环境配置、内网地址、设备标识、用户名路径、会话内容、录音及图片/视频元数据。合成测试使用可辨识的样本或运行时生成值，避免粘贴生产格式的真实配置。标准 Android 路径、模拟器地址和第三方版权信息需人工区分。

`.gitignore` 不会删除历史对象，也不会保护已经跟踪的文件。若发现真实凭据，先从公开候选中移除并核对暴露范围；已经对外暴露的凭据另行撤销/轮换。扫描通过仅表示未发现所覆盖特征，不能保证不存在任何秘密。

## 源码与发行包分别验收

源码发布前要明确可构建范围。新 checkout 按 [FIRST-DEPLOY.md](FIRST-DEPLOY.md) 验证已锁定的公开输入、校验和、下载与构建步骤；旧增量链依赖本地快照和回执，不能用它代替首次构建。由独立目录运行并分别记录构建、安装和功能结果；不得借用维护者私人目录，也不能将构建成功等同于账号、模型和设备内开发环境已经就绪。

APK、运行时快照、Debian/PRoot、ASR/Codex 可执行文件和模型分发另行验收：

- 逐项对照实际随包内容与许可，不仅检查源码目录中的声明是否存在。
- 对适用的 GPL/LGPL 组件，按对应版本及分发形式准备对应源码、构建/修改脚本和可履行的源码提供方式。一个浮动上游主页链接或笼统“源码要约”不作为本项目完成检查的证明。
- 自有版本号、签名、更新地址、下载源和发布脚本必须指向自有发行渠道；不能沿用公开测试签名或误向原作者仓库上传、替换资产。
- 新下载的 snapshot/rootfs 以及最终 APK 内部再做凭据、用户数据和许可检查，不能用源码扫描结果代替二进制检查。
- 设备验收和公开发布均遵守当轮授权；准备文档和本地扫描不等于创建 GitHub 仓库、发布 Release 或部署 APK 的授权。
