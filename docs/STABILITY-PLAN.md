# 第三阶段：真机前稳定性与交付

目标：将文件适配验证过的 APK 整理为可重复验收、可追溯、可下载的真机候选版本。故障注入仅用于专用模拟器，不清除用户数据。

| 步骤 | 验收条件 | 状态 |
| --- | --- | --- |
| 1. 安装包清单 | 双 ABI 的文件大小、摘要、签名、版本和来源固定 | 完成 |
| 2. 设备预检 | 明确设备、ABI、SDK、页大小、应用和运行时状态 | 完成 |
| 3. 冷启动 | 新进程启动、鉴权恢复、原会话和文件保留 | 完成 |
| 4. 引擎异常恢复 | 杀死精确匹配的 app 自有引擎，观察新 PID 自动恢复，无重复实例 | 完成 |
| 5. 后台/锁屏 | 实际 Agent 发起至少 5 分钟任务；持续写入证据，核对任务结束结果 | 完成 |
| 6. 模型失败重试 | 只为独立测试 provider 制造失败；能看到错误，恢复后请求成功 | 完成 |
| 7. 统一验收与交付 | 一条验收入口、可校验交付目录、实际可访问的 LAN 下载 URL | 完成 |
| 8. 仓库与真机矩阵 | 推送报告、安装流程、已知边界及后续路线 | 完成 |

本轮不把模拟器结果当成 HyperOS/ARM64 实测，不承诺任务可在引擎崩溃后自动续跑。文件系统崩溃一致性、插件 ABI 升级适配及自定义 preset 单独列入后续。

本轮结果与复现命令见 [STABILITY.md](STABILITY.md)。后续按真机基础验收、交互、HyperOS 后台、平台插件、稳定接口、自有发行六个步骤推进。
